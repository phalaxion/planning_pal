Fix the broadcast hot-spot (high impact) What I observed
broadcastStateToAll (internal/hub/room.go) iterates clients to build a recipients list, then for each recipient iterates all clients again to create per-recipient participant arrays. That is O(n^2) CPU and alloc work for each broadcast. With N participants and many frequent votes this becomes the dominant cost and will kill CPU/memory.
Why it matters

If a room has hundreds of participants, each vote leads to O(N^2) CPU and N JSON serializations. That will limit per-process throughput quickly.
Options (ordered by complexity / recommended) A) Best pragmatic change: send one common masked state to everyone + one small private message to each client containing only that client's true vote. This reduces per-broadcast work substantially (common payload serialized once; per-client small message of O(1)). Implementation plan:

In broadcastStateToAll:
Build maskedParticipants array once where all non-empty votes that should be hidden are replaced with "hidden".
Marshal a single state_update payload containing maskedParticipants and history, sent to all recipients (one serialized byte slice).
For each recipient, if recipient has a non-empty vote, send them an additional small message (type "private_your_vote" or a minimal state_update_you) that contains only their participant record (or only vote). The client merges that locally.
Pros: big CPU reduction, small change to client to accept the extra private message.
Cons: small change to client code (room.js). Still preserves vote privacy because only the owning client receives their actual vote.
B) Alternative: precompute a masked array and then for each recipient clone and patch only one element (less change on client). This still does per-recipient JSON but with much less work (changing one element vs rebuilding all). But A is better.

// go internal/hub/room.go (conceptual)
maskedParts := make([]*models.Participant, 0, len(clients))
for _, p := range clients {
  cp := *p.participant
  if r.phase == "voting" && cp.Vote != "" {
    cp.Vote = "hidden"
  }
  maskedParts = append(maskedParts, &cp)
}
commonPayload := mustMarshal(map[string]interface{}{ "roomId": r.ID, "phase": r.phase, "story": r.story, "facilitatorId": r.facilitatorID, "participants": maskedParts, "history": r.history })
msgCommon, _ := json.Marshal(models.Message{Type:"state_update", Payload: commonPayload})
for _, recipient := range r.participants {
  select { case recipient.send <- msgCommon: default: close(recipient.send) }
  // send private small message if recipient has a vote (their true vote)
  if own := recipient.participant; own != nil && own.Vote != "" {
    private := mustMarshal(map[string]interface{}{"youId": recipient.id, "participant": own})
    msgPriv, _ := json.Marshal(models.Message{Type:"private_update", Payload: private})
    select { case recipient.send <- msgPriv: default: close(recipient.send) }
  }
}
Limit history growth and payload sizes (medium effort) What I observed
Room.history is appended indefinitely and is serialized in every state update. For large rooms with many rounds history can become huge and blow memory and network throughput.
Recommendations

Cap number of history entries returned in each state_update (e.g., last 50 rounds). Keep full archive in persistent store only.
Make history payload optional or paginated: clients only fetch full history on demand (export or history panel).
Store full history in the persistent store and avoid serializing the entire store for every update.
Files to change:

internal/hub/room.go — adjust broadcast payload to include recent history only.
internal/store/* — ensure Save/List methods support pagination or retrieval of a range.
Reduce per-connection resource pressure and protect from slow clients (low effort) What I observed
Client.send channel size is 32 (internal/hub/client.go). That is fine, but room.broadcast uses non-blocking send and closes the channel when full. This will drop slow clients without a way to monitor or back off.
Recommendations

Increase send channel buffer modestly (e.g., 128) if you expect bursty updates.
Instrument and log occurrences where send channel is full (so you can detect slow clients).
Instead of immediately closing connection on a full send, consider one of:
Drop the message but keep the connection and track a slow-client counter; only disconnect if slow-client persists (N consecutive drops).
Or perform a best-effort: drop non-essential messages (debug), keep essential ones.
Tune ping/pong intervals, writeWait constants, and ReadLimit to appropriate values for high-scale: e.g., reduce ping interval if many idle connections to avoid unnecessary writes.
Files:

internal/hub/client.go: adjust buffer size, add logging/metrics around default case in broadcast.
Avoid per-room goroutine explosion if rooms are many with few connections (operational) What I observed
GetOrCreateRoom starts a goroutine per room.run(). If you have thousands of rooms you have thousands of goroutines. Goroutines are cheap but still have overhead and each room holds timers, channels, and memory.
Recommendations

It's OK to keep per-room goroutine for moderate scale, but for tens of thousands of rooms consider:
Evicting idle rooms sooner (configurable cleanup delay). Current cleanup is 5s — you might want different policies depending on load. But very many rooms with 0 participants aren't created; rooms are created on first connect. So main risk is many active small rooms.
Consider pooling/worker approach for rooms if needed, or partition rooms across instances.
Horizontal scaling / multi-instance architecture (mid-term, major) What I observed
Current design stores all room state in-memory inside a single binary's Hub. That prevents horizontal scaling without sticky routing.
Options: A) Sticky routing (simplest)

Keep current single-process room ownership model, and use a load balancer configured to route all WebSocket connections for a given room ID to the same backend instance (hash on URL path or room cookie).
Pros: minimal change to code.
Cons: capacity limited by instance size; uneven distribution possible.
B) Sharding with consistent hashing (recommended if you want multiple instances but keep in-memory room ownership)

Implement a short function at the load balancer or a proxy that hashes room ID and routes to appropriate backend instance.
Manage instance list via config or service discovery.
Pros: still minimal code change; balanced room distribution possible.
Cons: requires external routing config.
C) Shared-state with pub/sub (scalable)

Make each backend instance able to accept any client, but move the authoritative room state into a shared store or coordinate via a message broker (Redis pub/sub, Redis Streams, NATS).
Approach:
Keep each server instance as a WS front-end that subscribes to a Redis channel for room updates (channel name = room:{id}).
When a client sends a command, front-end publishes the command to a single logical room owner process or to a stream that is processed by a worker that owns the room state (worker can be elected via Redis lock or using a durable consumer group).
The room owner applies state and publishes new state to room:{id} channel; each front-end instance listening to that channel forwards to local clients in that room.
Pros: can scale horizontally, provides redundancy, allows using multiple machines for many connections.
Cons: architectural change and complexity.
Files/areas to modify for C:

Introduce a room-worker service (or make Hub use Redis/NATS).
Replace in-memory GlobalHub with a distributed coordinator.
Persistence: make saving asynchronous and durable (low-medium) What I observed
The room handles saving a RoundResult synchronously in handleClientMessage new_round; r.store.Save can be slow for SQLite or file IO and blocks room.run.
Recommendations

Save history asynchronously: push RoundResult to a background goroutine or worker queue (buffered) so room.run is not blocked by slow IO. If Save fails, log and retry in background, and return an error to the facilitator if necessary.
Alternatively, use a transactional DB (Postgres) for better concurrency under heavy write load.
